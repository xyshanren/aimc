# 看板 Phase 3 — 信息架构重排 + UI 现代化设计 (待评审)

> 2026-09-05 · 基于生产库近 14 天真实使用数据 + 开源竞品面板调研。
> 前置: 指标体系统一 Phase 1/2 已上线 (docs/dashboard-metrics-plan.md)。本文档只做设计, 未实施。

---

## 1. 调研结论

### 1.1 生产库使用数据 (ubuntu2401, 近 14 天)

| 发现 | 数据 | 对设计的含义 |
|---|---|---|
| **单用户自用为主** | 近 7 天 1286 请求中 caller_id=1 占 1250 (97%), api_keys 6 把仅 4 把 7 天内用过 | 不需要多租户式复杂度; 「按用户」「Key 管理」是低频功能 |
| **量级小、非秒级监控** | 日均 11~868 请求 (8/4 峰值 868), 无凌晨流量 | 概览不需要监控大屏式密度; 60s 轮询足够 |
| **晚间活跃** | 请求集中在 10-12 点 + 19-23 点 | 个人作息; 无告警值守需求, 但早上打开看板应一眼看到夜间发生了什么 |
| **tier:strong 绝对主力** | strong 985 (77%) > flagship 155 > balanced 125; 其余 tier 合计 <1% | 概览的分组视图只需突出前 3 个 tier |
| **模型双寡头** | glm-5.3-flash + deepseek-v4-flash 占 71% 请求 | top 模型表格 5 行即可覆盖主要信息 |
| **省钱是核心价值** | 近 7 天实付 ¥6.8 vs 标价 ¥395 (省 98%) | 成本是最高频关注点 → 成本应是一级页面而非折叠卡 |
| **审查队列平时是空的** | promotion_review / cross_source / 模型组建议 pending 全部 = 0 | 待处理/待审建议卡常年占着三列黄金位置却无事可看 → 应降级为全局 badge + 收进子页 |
| **请求明细无入口** | request_transcripts 已积 1566 条 / 103MB, 看板没有任何日志查看页 | 排障要登 VM 查库 → 竞品全部把「请求日志」当一级页面, 这是最大功能缺口 |

### 1.2 竞品面板 IA 模式 (LiteLLM Admin UI / NewAPI(one-api 系) / Helicone / Langfuse)

1. **无一例外是「侧边栏导航 + 分区页面」**, 没有竞品把全部功能堆在一页长滚动。典型分区: Dashboard(概览) / Requests or Logs(请求日志) / Usage(用量分析) / Spend(成本) / Providers or Channels(渠道) / Keys & Teams / Settings。
2. **请求日志是一级公民**: Helicone 的 Requests 表 (延迟/token/成本/状态, 点开看明细)、LiteLLM 的 Logs、NewAPI 的日志页——都是排障第一入口。AIMC 缺失。
3. **概览页 = 趋势图主视觉 + 少量 KPI**, 不放运维细节; LiteLLM 概览甚至是 "Big Number + 图表" 极简式。
4. **运维/审查类收进子页**, 通过 badge 提醒积压, 不占概览。
5. **视觉语言趋同**: 分层背景 (页面底色 > 卡片面) + 极低对比边框 + 单一强调色 + pill 徽章 + 无竖线表格 + 大数字 KPI (Vercel/Linear/shadcn 风), 明暗双主题。

### 1.3 现状问题 (对照得出)

- 20+ 张卡单页 3 列长滚动, 全部同时轮询: 视觉噪音大、想找某个功能要长距离扫视、无谓 API 压力。
- 信息优先级倒挂: 常年空队列的「待处理/待审建议」占黄金位, 而核心的「省钱」证据 (成本审计) 折叠在下面。
- 无请求日志页 (唯一的功能缺口, 需后端配合)。
- 视觉: 重边框卡片 + 密集小字表格, 与现代面板审美脱节 (但底子好: CSS 变量体系/明暗双主题/fmt 模块都已就绪)。

## 2. 信息架构方案 (Phase 3a)

### 2.1 总体结构: 侧边栏 + 6 页, 零构建哈希路由

```
┌──────────────────────────────────────────────────────────────┐
│ status-bar:  AIMC · 服务状态 ● 运行中        [待处理 1] [建议 0] │  ← 全局顶栏 (跨页)
├──────────┬───────────────────────────────────────────────────┤
│ ◆ 概览    │  页标题 + 时间范围 (24h/7d/30d, 跟随全局)           │
│ ◆ 成本    │                                                   │
│ ◆ 用量    │   当前页卡片 (2 列自适应网格)                        │
│ ◆ 渠道    │                                                   │
│ ◆ 情报    │                                                   │
│ ◆ 运维    │                                                   │
│          │                                                   │
│ (底部)    │                                                   │
│  周报     │                                                   │
│  登出     │                                                   │
└──────────┴───────────────────────────────────────────────────┘
```

- 路由: `#/overview` `#/cost` `#/usage` `#/channels` `#/intel` `#/ops` — hashchange 切换, 直链可分享/刷新还原; `<768px` 侧边栏折叠为顶部横向 tab。
- **轮询优化: 只轮询当前可见页的卡** (切页时 stop/start 对应 loader), 预计看板 API 压力降 60%+。
- 顶栏保留: 品牌 + 服务状态点 + **待处理/待审建议改为 badge** (有积压才显示数字, 点击跳对应页); 时间范围选择器从成本卡提升为页头全局控件。

### 2.2 页面与卡片映射 (旧 → 新)

| 新页 | 内容 | 来源卡 |
|---|---|---|
| **概览** `#/overview` (默认) | 4 KPI (Token/请求/Cache 命中率/Cache 节省) + 标价vs实付趋势图 + Top 模型表 (5 行) + 分组概览 (前 3 tier) + 今日摘要 (夜间请求/错误/新增告警) | 实时状态、用量统计(top5)、组路由成功率摘要、限额预警摘要(仅异常时) |
| **成本** `#/cost` | 成本审计 (tabs 按模型/分组/用户) + Cache 节省明细 (按渠道/按模型) | 原两卡平移, 时间范围用全局控件 |
| **用量** `#/usage` | 用量统计日表 + 路由成功率明细 + **请求日志 (新)** | 用量统计、组路由命中率; 新增请求日志页 (见 2.3) |
| **渠道** `#/channels` | 渠道 + 价格 (搜索/编辑 drop_params) + Model Registry + Groups (搜索) | 原两卡平移 |
| **情报** `#/intel` | 优惠情报 + 优惠审查 + 待确认能力变更 + 周报 | 原四卡平移; 周报从底部升入本页 |
| **运维** `#/ops` | 数据新鲜度 donut + 限额预警 (完整表) + 账号管理 + Key 管理 + 采集源管理 + 交叉源核查 + 待审建议(完整列表) | 原右栏全部 + 数据新鲜度; 低频操作集中一页 |

- 顶栏 badge 规则: 待处理 N>0 → 顶栏红点徽章, 点击跳 `#/ops`; 待审建议 M>0 → 点击跳 `#/ops`。**概览页在告警存在时显示一条「异常摘要条」**(替代原限额预警常驻卡)。

### 2.3 新增: 请求日志页 (唯一后端改动, Phase 3b)

- 列表: `GET /dashboard/api/requests?days=&status=&model=&key_id=&page=` — usage_logs 明细 (时间/模型/渠道/状态/token/延迟/实付), 分页 50/页。
- 详情抽屉: `GET /dashboard/api/requests/{id}/transcript` — request/response body 查看器 (JSON 折叠渲染), 排障不再登 VM。
- 复用 authFetch + METRIC_DEFS 格式; 列表默认只显示 7 天。

## 3. UI 视觉方案 (Phase 3c)

### 3.1 设计 tokens (在现有 CSS 变量体系上改值, 不换体系)

```css
:root {
  /* 分层背景: 页面底 < 卡片面 < 悬浮层 (替代"重边框"的层次手法) */
  --bg-base: #0b0e14;  --bg-surface: #11151d;  --bg-elevated: #1a2029;
  --bg-hover: #161c26;
  /* 边框全面降对比: 只留一条发丝线 */
  --border-default: #232a35;  --border-muted: #1a2029;
  /* 文字三级 */
  --text-primary: #e8edf4;  --text-secondary: #9aa7b8;  --text-muted: #5d6879;
  /* 强调色仅 1 个 (品牌蓝), 语义色只用于状态 */
  --color-accent: #4d9fff;  --color-success: #3dd68c;  --color-warning: #f0b429;  --color-danger: #f6685e;
  /* 形状: 圆角统一 10/14, 间距保持 4 的倍数 */
  --radius-md: 10px;  --radius-lg: 14px;
  /* 字号阶梯 (现状过散) */
  12 / 13 / 14(正文) / 16 / 20 / 28(KPI 大数字)
}
```

浅色主题同步这套层级 (已有 `prefers-color-scheme: light` 块, 改值即可)。

### 3.2 组件规格

| 组件 | 现状 | 目标 |
|---|---|---|
| 卡片 | 1px 实边框 + 标题行 + 折叠箭头 | `bg-surface` 面 + 发丝线边框 (或无边框+阴影), 圆角 14, 标题 13px medium, **去折叠箭头** (页面化后不再需要省高度) |
| KPI 卡 | 小数字 16px 挤在网格里 | 大数字 28px + 12px 灰标签 + 环比小字 (可选), 无边框色块 |
| 表格 | 全边框密排 + 竖线 | 去竖线, 表头 11px 大写灰字, 行 hover 高亮, 数字右对齐等宽字体 |
| 徽章/状态 | 彩色文字散落 | pill 徽章 (半透明底色 + 语义色文字) |
| 导航侧边栏 | 无 | 240px, 图标+文字, 当前页 `bg-hover` 高亮; <768px 折叠为顶部横滚 tab |
| 图表 | Chart.js 默认 + 15% 填充 | 线宽 1.5, 去点 (hover 显示), 网格用 `--border-muted`, 双系列用 强调色+成功色 |
| 按钮 | 多种杂色 | 主按钮=强调色实底, 次按钮=透明+边框, 危险=语义红; 尺寸统一 sm/md |

### 3.3 保留与不变

- 零构建约束: 纯 CSS 变量 + vanilla JS, 不引入 Tailwind/组件库 (与项目「保持零依赖」原则一致)。
- `authFetch` + localStorage `aimc_dashboard_token` 鉴权链路不动。
- Chart.js / htmx 继续使用; htmx 卡片随页面切换只触发当前页。
- 明暗双主题、全部现有 API、现有测试 (后端零改动, Phase 3b 除外)。

## 4. 实施分期

| 期 | 内容 | 改动面 | 预估 |
|---|---|---|---|
| **3a 信息架构重排** | 侧边栏+6 页哈希路由、卡片重排、顶栏 badge、全局时间范围提升、按页轮询 | 纯前端 (index.html 重写 + app.js 路由/轮询调度) | 大 |

建议顺序: **3a → 3c → 3b** (先把骨架和观感立起来; 3b 涉及后端新增可单独评审)。每期独立 commit + 上产, 任一期可叫停。

## 5. 风险与待确认

- 风险: index.html 是全量重写级改动, e2e 里若断言了看板 DOM 结构需同步 (待 grep 确认, 预计无); 3a 后旧书签/直链 `?range=` 仍有效 (hash 与 query 共存)。
- **待确认 1**: 导航用侧边栏 (本文方案, 竞品主流) 还是顶部 tab (更省横向空间)?
- **待确认 2**: 请求日志页是否需要 response body 查看? (涉及 transcripts 103MB 的读取暴露, 建议仅 admin key 可看)
- **待确认 3**: 折叠交互彻底移除 (页面化后每页内容已不多), 还是保留个别长表 (如用量统计) 的折叠?
- **待确认 4**: 3c 视觉是否一步到位改 tokens (全局观感突变), 还是先只改 IA、皮肤后置?
