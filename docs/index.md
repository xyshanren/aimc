**400 failover 换路 + 非流式失败分类落库 + 失败链落库（2026-10-22，V6.18）**：生产实录（10-22 00:16，hermes/shy 请求 tier:balanced）——上游 sensenova_official/lixiaoy + sensenova-6.8-flash-lite 返 400 `inference request is invalid`，**同一条路连撞 3 次**（00:16:12.4 / 00:16:13.0 / 00:16:13.6），白烧 1.95s 后把 400 透传给客户端，hermes 随即转本地 ollama 兜底链（00:16 起后续请求都走本地，00:44 才有成功的云端请求）。**① failover 空转**：400 判 client_error 不进 cooldown，重选候选时同一条路仍是最优 → "重试 3 次"实为"同一处撞 3 次"。修：router 的 `select_channel` / `_select_by_group` / `select_best_channel` 新增 `exclude_pairs`，routes 层把已试失败的 (account_id, 成员 model) 在**本次请求内**排除，每跳必然换路；候选用尽时**回放最后一次上游失败响应**而非合成 503（503 会掩盖上游真因，且对客户端是可重试语义而 400 不可重试——合成 503 会让客户端对不会自愈的请求反复重试）。**② 非流式失败无分类**：`_schedule_usage_log` 只在响应含 usage 时落详细行，4xx/5xx 响应体无 usage → 落库行 error_type/error_code/error_msg 全空（生产近 3 天 224 条 400 + 283 条 429 + 19 条 5xx 空），响应体非 JSON 时连行都不落（请求在用量页完全不可见）。修：与流式路径同构，status≥400 走 `classify()` 补分类（非 JSON 错误体也照落，不再整行丢失）；**成本口径不变**（失败行仍走原 usage/cost 计算，cost_estimate=0.0，与存量一致，不改成本页统计）。**③ 失败链只在校验中**：`usage_logs.failed_channels` 列全表 0 条非空，失败链只在响应体/响应头，看板无法下钻。修：routes 层逐跳累积失败链下传 proxy 落 `usage_logs.failed_channels`；看板请求日志列表显示错误分类（状态列 tooltip + 中文标签），详情抽屉新增"错误分类与失败链"表格（逐跳渠道/账号/状态/分类/错误）。**连带修**（生产部署后验证发现）：ORM 列原为 `Column(JSON)`，SQLAlchemy 默认把 `None` 序列化成 JSON 字面量 `'null'` 字符串而非 SQL NULL，使「`failed_channels IS NOT NULL`」把全部成功请求算成有失败链；改 `JSON(none_as_null=True)` + 迁移 `2026_10_22_v6x_failed_channels_null.py` 清理已写入的 `'null'` 行。回归 `tests/test_v618_400_failover_chain.py`（10 项）+ `tests/test_v618_chain_db.py`（2 项）。决策表见 [dev/architecture.md](dev/architecture.md) 2026-10-22 行。

**minimax 2056 Token Plan 耗尽误分类修复 + 手动恢复入口补齐（2026-10-21，V6.17，aliy-hy 上产，全量 1002 绿）**：用户报待处理栏 `minimax_compat: rate_limited (2055s) — 已达到 Token Plan 用量上限…(2056)` 在官方控制台 5h 额度已刷新后既不自愈也无手动恢复入口。三层根因：① **分类错**——minimax 把**所有** 429 的 `error.type` 都标 `rate_limit_error`（数字码 (2056) 只在 message 尾），命中 V6.7 限流兜底（error_classifier step 2.5）抢在 message 配额匹配（`已达.+?上限` 本可命中 QUOTA_EXHAUSTED）之前 → 误判瞬时限流 → 账号级冷却+指数退避（300s 基准封顶 3600s），**接不上 V6.15 配额恢复探测**（那只对 quota 桶隔离路径生效），GET /models 探活零 token 探不到 Token Plan 配额（配额耗尽期间每分钟 200 实证）——上游窗口刷新后 AIMC 白冷最多 1h（本次实例 00:58 冷却到期后流量立刻回切 200，实证"恢复永远晚一拍"）；② **确认恢复按钮形同虚设**——ack-recover 调 `mark_success` 被 V6.4.x 迟到成功护栏 early-return（冷却内直接 return），对账号级冷却中的账号什么都不清（V4.9 造端点在护栏之前，V6.4.x 加护栏没回头改端点）；③ **桶隔离状态不可见**——模型桶隔离不设账号级 cooldown，待处理栏五类目都接不住。修复：**A 分类**——`_PLAN_EXHAUSTED_HINT`（升级套餐/购买积分/Token Plan 上限）豁免限流兜底（豁免条件=套餐话术**且**命中配额关键字，只让"本该判配额"的情况落到 §4，TPM/RPM 限流不受影响），2056 判 QUOTA_EXHAUSTED 走桶隔离+恢复探测；套餐窗口类无绝对重置时间时桶冷却用 **5h**（原 3600s 会在窗口耗尽期内反复到期→重撞→升级 needs_human）；**A2** 恢复探测不再被 needs_human 掐断（`quota_buckets_due_for_probe` 不跳过 needs_human——探测是"窗口是否重置"的观察而非路由失败；manual_disabled 仍不探）；**A3** `mark_success(force=True)` 越过迟到成功护栏且同时清该账号全部模型桶隔离+探测节拍（清桶须在 state 检查之前——cleanup 会清掉过期 _state 条目而 5h 桶可能还活着）；**B/C** ack-recover 改 force=True + 待处理栏 cooldown_degraded 也渲染确认恢复按钮；新增待处理栏第 6 类目 **「⏳ 配额桶隔离中」**（quota_bucket）。回归 9 项（test_error_classifier 生产真实响应体判配额 + TPM 限流不误伤；test_v615 needs_human 桶继续探 + manual_disabled 仍不探；test_v64x force 复位清冷却/清桶；test_v631 桶类目可见 + needs_human 不重复），全量 1002 绿。生产部署：服务器树 9 commits 落后且带 scp 残留（SF 30003 手改副本等，`git stash push -u` 收进 stash `stale-scp-residue-20261021` 可找回）；重启后生产实测 2056 原始响应体 → `quota_exhausted`/18000s/needs_human=True、TPM 限流仍 `rate_limited` 300s、served app.js 含新类目。决策表见 [dev/architecture.md](dev/architecture.md) 2026-10-21 行。
