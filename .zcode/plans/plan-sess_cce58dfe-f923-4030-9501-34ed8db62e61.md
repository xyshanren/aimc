# 采集系统综合优化计划

## 背景与根因

经探索确认，飞书告警刷屏的**三个根因**（今日两个修复未覆盖）：

1. **model_list 源 401 死循环**：7 个源（deepseek/glm/qwen/stepfun/sensenova/hunyuan/moonshot）配了 `api_endpoint` 但无可用 API key → 每次 batch 都 401 → `handle_fetch_error` → `send_alert`。4 小时内 75 次告警。
2. **error_count pickle 重置**：`handle_fetch_error` 读 `source.error_count`（内存 dataclass），APScheduler 每次 tick 反序列化全新副本 → error_count 永远 =1 → 永远走"首次失败"分支 → 永远不达到 3 次自动禁用。（与 `has_changed` 的 `last_hash` pickle bug 同类，但上次只修了 `has_changed`）
3. **`_alert_low_confidence` 无 throttle**：低置信度解析结果调用 `send_alert(message)` 不带 `key`/`silence_seconds` → 完全不节流 → 每次低置信度都发飞书。

**批量间隔 bug**：`start_scheduler` 用 `min(poll_interval)` 作为 provider 的 batch 间隔 → 86400s 的 model_list 源被 900s 的 web_page 源拉低到每 15 分钟跑一次 → model_list 源每天被采 96 次而非 1 次。

**覆盖率问题**：11 个 model family vs 15 个 crawled provider，但存在命名不一致（`step` vs `stepfun`、`kimi` vs `moonshot`），3 个 benchmark 源文件已写但从未注册。

#### 1.2 修复 error_count pickle 重置
**文件**: `intelligence/healer.py` `handle_fetch_error` (446-463 行)

从 DB 读权威 error_count（与 `has_changed` 读 DB last_hash 同模式）：

效果：error_count 正确累加 → 3 次失败后自动禁用 + 2h 静默 → 不再每 15 分钟告警。

### 阶段 2: 修复批量间隔 bug + 自适应降频

#### 2.1 per-source 独立调度（替代 min 批量间隔）
**文件**: `intelligence/scheduler.py` `start_scheduler` (99-122 行)

当前：一个 provider 一个 batch job，间隔 = `min(所有源的 poll_interval)`。
改为：按 `poll_interval` 分组调度，同间隔的源共享一个 job：

```python
# 按 (provider, poll_interval) 分组, 而非只按 provider
from collections import defaultdict
by_provider_interval: dict[tuple[str, int], list] = defaultdict(list)
for source in sources:
    interval = source.poll_interval or DEFAULT_POLL_INTERVALS.get(source.source_type, 900)
    by_provider_interval[(source.provider, interval)].append(source)

for (provider, interval), group_sources in by_provider_interval.items():
    scheduler.add_job(
        _run_provider_batch,
        trigger=IntervalTrigger(
            seconds=interval,
            jitter=min(300, max(1, interval // 20)),
        ),
        args=[provider, group_sources],
        id=f"batch_crawl_{provider}_{interval}",
        name=f"批量采集: {provider} ({interval}s, {len(group_sources)} sources)",
        replace_existing=True,
    )
```

效果：deepseek 的 900s web_page 源每 15 分钟跑，86400s model_list 源每天跑一次。不再交叉污染。

#### 2.2 无变化自适应降频
**文件**: `db/models.py` `IntelSource` (382-396 行) + `db/init_db.py` `ensure_migrations`

```python
consecutive_no_change = Column(Integer, default=0, comment="连续无变化次数")
```

迁移：
```sql

```

**文件**: `intelligence/differ.py` `has_changed` (76-77 行, 83-91 行)

无变化时递增 `consecutive_no_change`，有变化时归零：
```python
# 哈希相同 → 无变化

    return False

# ... 相似度高 → 无变化

    await _update_source_hash(source, new_hash, new_content)

# 有变化 → 归零 (在 _update_source_hash 里做)
```

新增 `_increment_no_change` 函数：更新 DB `consecutive_no_change += 1`。

**文件**: `intelligence/scheduler.py` `_run_source_task` 开头

在执行采集前检查自适应降频：
```python
# 自适应降频: 连续无变化次数过多 → 跳过本次 (降频效果)
no_change = await _get_consecutive_no_change(source)
if no_change >= 10:
    # 10 次以上无变化 → 降频到 1h (跳过非整点 batch)
    # 用 last_check_at 判断是否到了降频后的间隔
    interval_multiplier = 4 if no_change >= 10 else 1  # 4x = 1h for 15min source
    # ... 简化实现: no_change>=10 且距上次检查不足 1h → skip
```

简化方案：`consecutive_no_change >= 4` 且距 `last_check_at` 不足 `poll_interval * 4` → 跳过。`>= 10` 且不足 `poll_interval * 8` → 跳过。
